# QA and load test run: 5 November 2026

The functional QA and load test asked for on 5 Nov, run on the current code (branch `claude/great-brown-e2uiyp`).
Every number below was measured in this run.

**Verdict: the hub is functional.** Every tool works end to end at every plan level, the plan locks and limits hold,
payments work in test mode, and the admin panel works. One defect was found (test mode only) and fixed. Under load,
the app handled 500 webinar attendees and 500 paid members with 0 failures. A webinar spike *plus* 300 paid members
needs one setting raised (see section 4).

What this run cannot prove is the same as before: the real outside services (Razorpay, MSG91, AiSensy, Anthropic,
Gemini) with real keys, and Railway/Atlas speed. See section 6.

## 3. Load test (`scripts/loadtest/`)

The database was seeded with **10,000 accounts**: 8,051 free, 1,147 on the ₹1,999 plan, 605 on L1 and 197 on L2, with
45,027 events and this month's usage.

### Run A: 500 webinar attendees at once
500 people arriving over 50 seconds. Each signs up by OTP and uses every webinar tool, 2–8 s apart. That's harder than
a real webinar.

- **57,642 requests, 0 failed.**
- All 500 results were saved: 500 Readiness Scores, 500 Niche Snapshots, 500 case answers, 500 briefs and 500 LinkedIn
  checks (counted in the database).

| Step | Median | 95% within |
|---|---|---|
| Login code sent / checked | 0.04 s / 0.02 s | 0.07 s / 0.04 s |
| Screens without AI (home, readiness, goal, LinkedIn score, cases, file) | 0.002–0.02 s | 0.05 s |
| Niche Snapshot (AI) | 7.7 s | 26 s |
| Case scoring (AI) | 16 s | 28 s |
| Meeting Brief (search + AI) | 19 s | 47 s |

CPU: 100% at the arrival peak, 30% on average.

### Run B: 500 paid members at once
Existing ₹1,999, L1 and L2 members using the paid tools: home, cases, decks (made and downloaded), visuals, Action Hub
chat, Akshat AI, Offer Card, stories, inbox, file, and the L2 tools (outreach, proposals, social posts, radar).

- **15,421 requests, 0 failed.**
- 78 deck requests were correctly refused because those members had used their monthly deck limit.
- Medians: deck made 6.1 s, PowerPoint/PDF download 0.004 s, AI tools 6.0 s (the AI time itself), screens 0.002–0.009 s.
- Rerun with Akshat's material in the knowledge base (B2), so Akshat AI takes its real answer path: 8,089 requests,
  0 failed, Akshat AI 6.0 s median.

### Run C: webinar spike + 300 paid members (800 people), default settings
- Attendees: 32,732 requests, **0 failed**.
  - Medians: Niche Snapshot 13 s, case scoring 21 s, brief 20 s; all within 30 s.
- Members: 6,508 requests, **145 failed (2.2%)**. Every failure was the designed "AI is busy, try again" answer.
  - About 10% of members' AI requests were turned away, after waiting 15 s for an AI slot.
  - Each time, the use was given back. The real page retries once by itself; the load tester doesn't.

### Run D: same as C with `LLM_MAX_CONCURRENCY=96`
- Attendees: 39,254 requests, **0 failed**.
  - Niche Snapshot, case scoring and brief all about 6 s median, 95% within 11–12 s.
- Members: 7,027 requests, **0 failed**; AI tools 6 s median.
- CPU: average 34%, peak 100% at arrival.

## 4. Recommendation from the load test

The app's AI queue allows `LLM_MAX_CONCURRENCY` calls at once per worker. The default is 48, so 96 with 2 workers.

- **Webinar alone:** 48 is enough (runs A and B: 0 failures).
- **Webinar while paid members are busy:** 48 turns away about 10% of members' AI requests during the spike (run C);
  96 handles it with no failures and faster answers (run D).
- **Before the first webinar:** check the Anthropic account's rate limit (Console › Limits).
  - If it allows about **1,900 requests a minute**, set `LLM_MAX_CONCURRENCY=96` on Railway.
  - If it doesn't, keep 48. Members may see "busy, try again" during the QR minutes, and they never lose a go.
